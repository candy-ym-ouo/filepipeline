# 02 · 系统架构（多模块分层）

> 本文档定义系统的整体架构：进程形态、分层结构、模块职责、依赖方向、数据流与并发模型。
> 分层原则：**依赖只允许自外向内、自下而上，禁止反向引用**。

---

## 1. 进程形态

系统由**两个独立进程**组成，共享同一 SQLite 数据库文件与本地文件存储目录：

```
┌─────────────────────┐          ┌─────────────────────┐
│     cmd/api          │          │    cmd/worker        │
│  HTTP API 服务       │          │  后台任务 Worker      │
│  ─ 接收上传          │          │  ─ 轮询待处理任务     │
│  ─ 查询/重试         │          │  ─ 执行阶段流水线     │
│  ─ 扫描回调接收      │          │  ─ 重试与退避调度     │
│  ─ 静态托管前端      │          │  ─ 等待/回收回调      │
└──────────┬──────────┘          └──────────┬──────────┘
           │ 共享                             │ 共享
           ▼                                 ▼
   ┌─────────────────────────────────────────────┐
   │  SQLite（tasks / task_events / migrations）  │
   │  +  本地文件存储目录（data/files/）            │
   └─────────────────────────────────────────────┘
```

- API 进程：面向用户（上传、查询、重试、回调接收、前端页面）；
- Worker 进程：面向任务（阶段执行、重试调度、回调等待）；
- 二者可同机部署，也可分离部署（文档假设同机，通过配置项指定数据库与存储路径）。

## 2. 分层结构

```
┌──────────────────────────────────────────────────────────┐
│ cmd/         进程入口（薄壳：装配依赖 + 启动 + 优雅关闭）     │
│   ├─ cmd/api        API 服务入口                            │
│   └─ cmd/worker     Worker 入口                             │
├──────────────────────────────────────────────────────────┤
│ internal/api   HTTP 传输层（路由 / 处理器 / 中间件 / 静态托管）│
├──────────────────────────────────────────────────────────┤
│ internal/worker  后台调度层（轮询 / 领取 / 阶段执行 / 回收）   │
├──────────────────────────────────────────────────────────┤
│ internal/service  业务编排层（流水线 / 校验 / 提取 / 扫描 /   │
│                    重试策略）                               │
├──────────────────────────────────────────────────────────┤
│ internal/domain   领域层（任务 / 状态机 / 阶段 / 错误）        │
├──────────────────────────────────────────────────────────┤
│ internal/repository   持久化层（任务仓库 / 事件仓库）          │
│ internal/storage      文件存储层（落盘 / 读取 / 校验和）       │
├──────────────────────────────────────────────────────────┤
│ internal/migrate      迁移层（内嵌 SQL / 版本表）             │
│ internal/config       配置层（加载 / 校验）                   │
├──────────────────────────────────────────────────────────┤
│ web/   简单前端（静态资源，由 api 进程托管）                   │
│ migrations/  迁移 SQL 文件（embed 进 migrate 模块）           │
└──────────────────────────────────────────────────────────┘
```

## 3. 模块职责与依赖方向

依赖规则：**箭头指向被依赖方**。禁止环依赖；`domain` 不依赖任何内部模块。

```
 cmd/api ──► internal/config
 cmd/api ──► internal/api ──► internal/service
 cmd/api ──► internal/migrate ──► internal/repository(仅建库)
 cmd/api ──► internal/storage（上传落盘）

 cmd/worker ──► internal/config
 cmd/worker ──► internal/worker ──► internal/service
 cmd/worker ──► internal/repository

 internal/service ──► internal/domain
 internal/service ──► internal/repository
 internal/service ──► internal/storage

 internal/repository ──► internal/domain
 internal/storage    ──► internal/domain（错误类型复用）

 internal/api ──► internal/service（间接）/ internal/domain
 internal/worker ──► internal/service（间接）/ internal/domain
```

### 3.1 模块职责表

| 模块 | 职责 | 关键类型 |
| --- | --- | --- |
| `cmd/api` | 加载配置、执行迁移、装配 handler、启动 HTTP、优雅关闭 | `main` |
| `cmd/worker` | 加载配置、执行迁移、装配 worker、启动调度、优雅关闭 | `main` |
| `internal/config` | 从环境变量/参数读取配置、默认值、校验 | `Config`, `DBConfig`, `WorkerConfig` |
| `internal/domain` | 任务实体、状态/阶段枚举、状态机迁移表、领域错误、回调负载 | `Task`, `Status`, `Stage`, `TaskEvent`, `ScanResult`, `Err*` |
| `internal/repository` | SQL 访问封装：任务 CRUD、原子领取、事件写入、列表查询 | `TaskRepository`, `EventRepository`, `Repository` |
| `internal/storage` | 文件落盘/读取/删除、SHA-256 计算、随机文件名生成 | `Storage`, `LocalStorage` |
| `internal/service` | 流水线编排与各阶段实现、重试退避计算 | `Pipeline`, `Validator`, `Extractor`, `Scanner`, `RetryPolicy` |
| `internal/worker` | 轮询领取、阶段分派、回调等待与回收、优雅关闭 | `Worker`, `Processor` |
| `internal/api` | HTTP 路由、JSON 编解码、错误映射、回调签名校验、静态托管 | `Router`, `Handlers`, `Middleware` |
| `internal/migrate` | 内嵌迁移 SQL、版本表、顺序执行、事务包裹 | `Migrator` |
| `web` | 前端页面（非 Go，静态托管） | `index.html`, `style.css`, `app.js` |

## 4. 关键数据流

### 4.1 上传 → 校验 → 提取（正常路径）

```
用户 ──POST /api/v1/files──► api.Handlers.Upload
                              │ 1. 读取 multipart，检查大小（>10MiB → 413）
                              │ 2. storage.Save(file) → 随机文件名 + SHA-256
                              │ 3. domain.NewTask(...)  status=PENDING stage=VALIDATE
                              │ 4. repo.CreateTask(task)
                              │ 5. 返回 201 {task_id}
                              ▼
worker.Worker ──轮询──► repo.ClaimPending()（乐观锁，PENDING→PROCESSING）
                              ▼
worker.Processor ──► service.Validator.Validate(task)
                              │ 通过 → service.Pipeline.Advance(task)
                              ▼
worker.Processor ──► service.Extractor.Extract(task)  → 写摘要
                              ▼
worker.Processor ──► service.Scanner.Scan(task)       → 同步结果 或 异步等待
                              ▼
worker.Processor ──► 终态 SUCCEEDED / FAILED（事件全部落库）
```

### 4.2 失败与重试路径

```
阶段失败（attempts < max）
  → repo.UpdateTask(status=PENDING, attempts+1, next_run_at=now+backoff)
  → 事件表记录失败原因
  → Worker 在 next_run_at 后再次领取，从失败阶段重试

阶段失败（attempts >= max）
  → repo.UpdateTask(status=FAILED, error_code, error_message)
  → API 允许手动重试 POST /api/v1/tasks/{id}/retry
  → 重置 attempts=0，status=PENDING，从失败阶段重跑
  → 手动重试 3 次仍失败 → DEAD（死信）
```

### 4.3 异步扫描回调路径

```
worker ──► scanner.Submit(task)（向扫描服务提交）→ accepted
任务进入"等待回调"状态（SCAN 阶段，waiting=true）
外部扫描服务完成判定 ──POST /api/v1/scan-callback──► api.Handlers.ScanCallback
   │ 校验 HMAC 签名（callback_token）
   │ 更新 scan_verdict / scan_scanner / scan_at
   ▼
任务回到 PENDING（下一阶段 DONE）→ Worker 完成 → SUCCEEDED
若回调 30s 未到 → Worker 回收逻辑将任务重新置为可扫描 → 重投扫描请求
```

## 5. 并发与一致性模型

### 5.1 Worker 并发模型

- Worker 启动 `N=4` 个处理协程，共享一个轮询器；
- 轮询器每隔 `poll_interval=500ms` 领取一批任务（`batch=8`）分发给空闲协程；
- 每个协程串行执行单个任务的完整阶段链（单任务内不并行，保证阶段顺序）；
- 领取使用乐观锁（见文档 01 · 4.4），天然防并发重复处理；
- 所有协程共享同一个 `context.Context`，收到 SIGTERM/SIGINT 后：
  1. 停止轮询新任务；
  2. 等待正在执行的任务完成当前阶段（超时 10s）；
  3. 未完成任务释放回 `PENDING`（状态回滚 + lease 到期），随后退出。

### 5.2 租赁（Lease）机制

- 领取任务时写入 `leased_until = now + lease_seconds(30s)`；
- 崩溃恢复：Worker 启动时执行回收 SQL，将 `status=PROCESSING AND leased_until < now`
  的任务回滚为 `PENDING`（attempts 不变），保证"进程崩溃不丢任务"；
- 与"阶段成功推进"共用同一事务更新，避免状态与事件不一致。

### 5.3 一致性保证汇总

| 保证 | 机制 |
| --- | --- |
| 任务不重复处理 | 乐观锁原子领取 |
| 状态与事件一致 | 状态变更与事件插入在同一 SQL 事务 |
| 崩溃不丢任务 | Lease 回收（启动时 + 周期执行） |
| 重试不重复副作用 | 幂等键（task_id）+ 只读提取 + 等待态判定 |
| 终态不可变 | 更新语句带 `status IN (...)` 守卫 + 受影响行数校验 |

## 6. 配置项（internal/config）

| 配置 | 环境变量 | 默认值 | 说明 |
| --- | --- | --- | --- |
| HTTP 监听地址 | `PIPE_HTTP_ADDR` | `:8080` | API 监听地址 |
| 数据库路径 | `PIPE_DB_PATH` | `./data/pipeline.db` | SQLite 文件 |
| 文件存储目录 | `PIPE_FILE_DIR` | `./data/files` | 上传文件落盘目录 |
| Worker 并发数 | `PIPE_WORKER_COUNT` | `4` | 处理协程数 |
| 轮询间隔 | `PIPE_POLL_INTERVAL` | `500ms` | 轮询周期 |
| 批量领取数 | `PIPE_BATCH_SIZE` | `8` | 每轮领取上限 |
| 阶段最大尝试 | `PIPE_MAX_ATTEMPTS` | `3` | 每阶段重试上限 |
| 租约时长 | `PIPE_LEASE_SECONDS` | `30` | 领取后租约 |
| 扫描服务地址 | `PIPE_SCAN_URL` | `http://127.0.0.1:9090` | 外部扫描服务（可配置为 mock） |
| 扫描超时 | `PIPE_SCAN_TIMEOUT` | `5s` | 同步扫描超时 |
| 回调等待超时 | `PIPE_CALLBACK_WAIT` | `30s` | 异步回调最大等待 |

## 7. 架构决策记录（ADR）

| ADR | 决策 | 理由 |
| --- | --- | --- |
| ADR-1 | 采用 SQLite 而非 Postgres | 单机部署简单、零运维；迁移模块保持 SQL 文件形态，未来可切换驱动 |
| ADR-2 | 标准库 `net/http`（1.22+ 路由） | 无第三方框架，依赖面最小，符合"简单"原则 |
| ADR-3 | API 与 Worker 分进程 | 职责隔离：API 无状态可水平扩展，Worker 独占调度 |
| ADR-4 | 阶段由 Worker 串行驱动 | 单任务阶段强顺序，避免分布式编排复杂度 |
| ADR-5 | 前端用原生三件套 | 无需构建链，静态托管即用（非 Go，不计入行数约束） |
| ADR-6 | 领域层不依赖任何基础设施 | 状态机与业务规则可脱离 DB/HTTP 单测 |
