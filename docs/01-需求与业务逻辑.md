# 01 · 需求分析与业务逻辑扩写

> 本文档对项目提示词进行**功能与业务逻辑扩写**，是后续架构设计、代码实现与测试编写的
> 唯一需求基线。所有模块的行为必须与此处描述一致。

- **项目提示词（原文）**：
  > 用 Go 构建文件处理流水线，上传后执行格式校验、内容提取、扫描回调和失败重试；项目必须多模块分层、持久化任务并支持迁移，提供 API、后台 Worker、测试及验证。

---

## 1. 需求拆解

将提示词拆解为六项可验证的需求：

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| R1 | **文件上传** | 通过 API 上传文件，落盘并创建持久化任务，立即返回任务 ID |
| R2 | **格式校验** | 对上传文件做扩展名 / MIME / 魔数 / 大小 / 哈希完整性校验 |
| R3 | **内容提取** | 按文件格式解析并提取内容，输出结构化摘要 |
| R4 | **扫描回调** | 调用外部扫描服务获取判定；支持同步返回与异步回调两种模式 |
| R5 | **失败重试** | 每阶段失败自动重试（指数退避），超限进入失败态，支持手动重试 |
| R6 | **工程约束** | 多模块分层；任务持久化并支持迁移；提供 API、Worker、测试与验证；简单前端 |

## 2. 角色与用户故事

### 2.1 角色

| 角色 | 描述 |
| --- | --- |
| 上传者（调用方） | 通过 API 或前端上传文件，查询处理进度，对失败任务发起重试 |
| 扫描服务（外部） | 接收扫描请求（文件路径/元数据），返回 `clean` / `infected` / `error` 判定 |
| 运维人员 | 启动 API 与 Worker、执行迁移、查看任务健康度 |

### 2.2 用户故事

1. 作为上传者，我上传一个 `.txt` 文件，期望立即拿到任务 ID，随后能查询到
   "校验通过 → 内容提取完成 → 扫描为 clean → 处理成功"的完整轨迹。
2. 作为上传者，我上传一个被篡改扩展名的文件（`.txt` 实为二进制），期望任务在
   **校验阶段**被拒绝，并给出明确失败原因。
3. 作为上传者，我的扫描服务暂时不可用，期望任务自动重试，而不是立刻失败。
4. 作为上传者，任务最终失败时，我希望通过"重试"按钮让流水线重新处理。
5. 作为运维人员，我希望重启进程后任务仍从上次断点继续，不丢不重。

## 3. 核心业务逻辑：五阶段流水线

### 3.1 流水线总览

每个上传文件对应一个 **任务（Task）**，任务在流水线中按固定阶段流转：

```
          ┌───────────┐     ┌───────────┐     ┌───────────┐     ┌───────────┐
  上传 ──► │ 1 校验     │ ──► │ 2 提取     │ ──► │ 3 扫描     │ ──► │ 4 完成     │
 (UPLOAD) │ VALIDATE  │     │ EXTRACT   │     │ SCAN      │     │ DONE      │
          └───────────┘     └───────────┘     └───────────┘     └───────────┘
              │ 失败             │ 失败             │ 失败
              ▼                 ▼                 ▼
          ┌──────────────────────────────────────────────────┐
          │ 5 失败处理：自动重试（退避）→ 超限 FAILED → 手动重试 │
          └──────────────────────────────────────────────────┘
```

### 3.2 阶段定义

| 阶段 | 常量 | 输入 | 产出 | 失败条件 |
| --- | --- | --- | --- | --- |
| 格式校验 | `VALIDATE` | 落盘文件 | 通过/拒绝 + 原因 | 扩展名、MIME、魔数、大小任一不合法；哈希不匹配 |
| 内容提取 | `EXTRACT` | 落盘文件 | 提取摘要（内容/统计） | 解析失败；内容超限截断仍失败 |
| 扫描回调 | `SCAN` | 文件路径 + 元数据 | 判定结果 + 扫描器信息 | 扫描服务错误、超时、判定为 `error` |
| 完成 | `DONE` | 全部产物 | 任务终态 `SUCCEEDED` | —（终态阶段，不重试） |

> 注意：**上传**（UPLOAD）在 API 层完成，不属 Worker 阶段；任务创建后立即进入
> `VALIDATE` 阶段等待 Worker 领取。

## 4. 任务状态机（Task State Machine）

### 4.1 状态定义

| 状态 | 常量 | 说明 |
| --- | --- | --- |
| 待处理 | `PENDING` | 已创建或等待重试，可被 Worker 领取 |
| 处理中 | `PROCESSING` | 已被某个 Worker 领取，正在执行当前阶段 |
| 成功 | `SUCCEEDED` | 流水线全部完成（终态） |
| 失败 | `FAILED` | 某阶段超过最大尝试次数（终态，可手动重试） |
| 死信 | `DEAD` | 手动重试也失败达到上限（终态） |

### 4.2 状态迁移规则（完整）

| 前置状态 | 事件 | 后置状态 | 触发方 |
| --- | --- | --- | --- |
| （新建） | 上传成功 | `PENDING` | API |
| `PENDING` | Worker 原子领取成功 | `PROCESSING` | Worker |
| `PROCESSING` | 当前阶段执行成功 | `PENDING`（进入下一阶段） | Worker |
| `PROCESSING` | 最后一个阶段（DONE）成功 | `SUCCEEDED` | Worker |
| `PROCESSING` | 当前阶段失败且 `attempts < max` | `PENDING`（同阶段重试） | Worker |
| `PROCESSING` | 当前阶段失败且 `attempts >= max` | `FAILED` | Worker |
| `FAILED` | 收到手动重试请求 | `PENDING`（从首个失败阶段重跑） | API |
| `FAILED` | 手动重试次数达到上限 | `DEAD` | Worker/API |

### 4.3 状态机约束（不变量）

1. 只有 `PENDING` 状态的任务能被领取，且领取必须是**原子的**（见 4.4）；
2. 只有 `FAILED` 状态的任务能手动重试，`DEAD` 不可重试；
3. `SUCCEEDED` / `DEAD` 为终态，任何入口都不得再流转；
4. 任务必须记录**当前阶段**与**当前尝试次数**，进程重启后据此续跑。

### 4.4 原子领取（防重复处理）

Worker 使用乐观锁领取任务，避免多 Worker / 多协程重复处理同一任务：

```sql
UPDATE tasks
   SET status = 'PROCESSING', version = version + 1, updated_at = now()
 WHERE id = ? AND status = 'PENDING' AND version = ?
   AND next_run_at <= now();
```

- 受影响行数为 1 才视为领取成功；
- 领取成功后按 `version` 判断是否发生过并发修改，冲突则放弃本次处理。

## 5. 阶段业务规则详解

### 5.1 格式校验（VALIDATE）

校验按固定顺序执行，任一失败即终止并记录首个失败原因：

1. **扩展名白名单**：`txt, json, csv, log, md, yaml, xml`；不在白名单 → 拒绝；
2. **MIME 类型**：依据扩展名推断期望 MIME，与实际探测值比对；
3. **魔数（Magic Bytes）**：
   - `txt/log/md` → 内容必须为可打印 UTF-8 文本（无 NUL 字节）；
   - `json` → 必须以 `{` / `[` 开头（可跳过空白）；
   - `csv` → 首行为文本字段，且无二进制特征；
   - `yaml/xml` → 与文本类同样要求（后续提取阶段再深度解析）；
4. **大小限制**：`0 < size <= 10 MiB`；空文件或超大文件 → 拒绝；
5. **完整性**：上传时计算 SHA-256 并随任务落库，校验阶段重算比对，不一致 → 拒绝。

**业务效果**：格式校验把"不符合要求的文件"挡在流水线最前端，节省后续提取与
扫描成本；`txt` 伪装成可执行文件的场景（如带 NUL 的伪文本）会在魔数检查中被识破。

### 5.2 内容提取（EXTRACT）

校验通过后按格式提取内容，产出 `extracted_summary`（限制 4 KiB，超出截断并标记）：

| 格式 | 提取策略 |
| --- | --- |
| `txt / log / md` | 读取前 N 行原文，统计行数、字符数、单词数 |
| `json` | 解析为 JSON，输出键列表 + 顶层类型 + 长度统计 |
| `csv` | 解析表头与行数，输出列名列表 + 前 3 行样例 |
| `yaml` | 输出文档顶层键列表（简化解析） |
| `xml` | 输出根元素与直接子元素名列表 |

提取规则：
- 提取失败（如 JSON 语法错误）→ 阶段失败，进入重试逻辑；
- 提取成功但内容为空 → 视为成功，摘要标记 `empty: true`；
- 提取过程**只读**打开文件，不修改原文件。

### 5.3 扫描回调（SCAN）

提取完成后将文件交给外部扫描服务判定。支持两种回传模式：

**模式 A · 同步返回**：Worker 调用扫描服务 HTTP 接口，在超时（默认 5s）内拿到
`{verdict, scanner, scanned_at}`，直接落库，进入下一阶段。

**模式 B · 异步回调**：Worker 调用扫描服务的"提交"接口，拿到 `accepted` 后任务
进入等待态；扫描完成后由外部服务反向调用本系统的 `POST /api/v1/scan-callback`
回传结果。回调协议见 5.3.2。

#### 5.3.1 判定结果

| verdict | 含义 | 任务走向 |
| --- | --- | --- |
| `clean` | 未发现风险 | 进入 DONE → `SUCCEEDED` |
| `infected` | 发现风险 | 任务结束（终态 `SUCCEEDED`，但标记 `scan_verdict=infected`，业务方据此处置） |
| `error` | 扫描服务自身错误 | 视为阶段失败，触发重试 |

#### 5.3.2 异步回调协议

```http
POST /api/v1/scan-callback
Content-Type: application/json
X-Callback-Signature: <HMAC-SHA256>

{
  "task_id": "t_01J...",
  "verdict": "clean",
  "scanner": "mock-antivirus",
  "scanned_at": "2026-01-01T12:00:00Z",
  "signature": "..."
}
```

- 签名使用任务创建时下发的 `callback_token` 计算（`HMAC-SHA256(body)`）；
- 签名不合法 → 400；任务不存在或已结束 → 404 / 409；
- 回调成功 → 任务更新扫描结果并进入 DONE；
- 回调失败（网络抖动）→ Worker 侧按"等待回调"轮询超时后**重投扫描请求**，
  保证最终一致（见文档 05 第 6 节）。

### 5.4 失败重试（RETRY）

重试是流水线的横向能力，作用于 `VALIDATE / EXTRACT / SCAN` 三个阶段：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `max_attempts` | 3 | 每个阶段的**独立**最大尝试次数 |
| 退避基数 | 1s | 第 n 次重试等待 `2^(n-1)` 秒 |
| 抖动 | ±20% | 随机抖动避免惊群 |
| 最大退避 | 30s | 退避上限 |

重试规则：

1. 阶段失败时 `attempts + 1`，并记录失败原因与时间；
2. `attempts < max_attempts` → 状态回 `PENDING`，`next_run_at = now + backoff`，
   等待 Worker 再次领取（**同一阶段**重试，不重跑已成功阶段）；
3. `attempts >= max_attempts` → 状态置 `FAILED`，记录最终错误；
4. `FAILED` 任务可手动重试：状态回 `PENDING`，`attempts` 归零，
   从**首次失败的阶段**重新执行；
5. 手动重试累计达到 3 次仍失败 → 置 `DEAD`（死信），不再自动流转。

**幂等性**：重试不得产生重复副作用——

- 内容提取只读、可重复执行，天然幂等；
- 扫描请求以 `task_id` 为幂等键，扫描服务对同任务重复请求返回已缓存结果；
- 异步回调以"任务当前是否处于等待回调态"为判定，重复回调直接忽略。

## 6. 业务规则汇总表

| 编号 | 规则 |
| --- | --- |
| BR-1 | 一次上传生成一个任务，任务 ID 全局唯一（`t_` 前缀 + UUID） |
| BR-2 | 同一文件重复上传生成独立任务（不做内容去重合并，保证可追溯） |
| BR-3 | 校验失败的文件**不进入**提取与扫描阶段 |
| BR-4 | 每个阶段独立计数尝试次数；重试只重跑失败阶段 |
| BR-5 | 扫描判定 `infected` 仍属处理成功（业务侧处置），`error` 才触发重试 |
| BR-6 | 终态任务（SUCCEEDED/DEAD）拒绝任何改写操作 |
| BR-7 | 所有状态变更必须写入 `task_events` 事件表（审计轨迹） |
| BR-8 | 任务领取必须原子（乐观锁），防止并发重复处理 |
| BR-9 | 文件最大 10 MiB，超限上传直接 413 拒绝，不创建任务 |
| BR-10 | 提取摘要上限 4 KiB，超出截断并在摘要中标记 |

## 7. 边界与异常场景

| 场景 | 系统行为 |
| --- | --- |
| 上传空文件 | 校验阶段拒绝：`size=0`，原因 `ERR_EMPTY_FILE` |
| 上传超大文件 | API 层 413 直接拒绝，不落盘、不建任务 |
| 伪造扩展名 | 魔数检查识破，校验失败 `ERR_MAGIC_MISMATCH` |
| JSON 语法错误 | 提取阶段失败，重试 3 次后任务 FAILED |
| 扫描服务 500 | SCAN 阶段失败，按退避重试；3 次后 FAILED |
| 扫描服务超时 | 同 500，按阶段失败处理 |
| 异步回调丢失 | Worker 等待回调超时（30s）后重投扫描请求 |
| 进程崩溃 | 任务停留 `PROCESSING`；重启后 Worker 将超过 `lease` 期限的
  `PROCESSING` 任务回收为 `PENDING`（见文档 05） |
| 重复回调 | 任务不处于等待态 → 幂等忽略 |
| 伪造回调签名 | 400 拒绝 |
| 并发领取 | 乐观锁保证只有一个 Worker 成功 |
| 前端重复点击重试 | 任务已非 FAILED → 409 冲突提示 |

## 8. 非功能需求

| 维度 | 要求 |
| --- | --- |
| 可用性 | API 与 Worker 可独立启停；任一崩溃不影响已持久化任务 |
| 一致性 | 任务状态与事件以数据库为准；进程重启可续跑 |
| 可观测性 | 事件表记录全部阶段流转；日志输出任务 ID 与阶段 |
| 安全性 | 回调签名校验；上传大小限制；文件以随机 ID 落盘避免路径穿越 |
| 性能 | Worker 并发 4 个协程处理；单任务各阶段串行 |
| 可维护性 | 模块分层清晰；迁移脚本可重复执行（幂等版本表） |
